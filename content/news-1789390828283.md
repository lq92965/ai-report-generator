# The Unit Test Is Now a Vibe Check

The pitch is irresistible. You describe a feature in plain English, an agent writes the code, and the tests pass. Green checkmarks everywhere. Ship it.

Then you look at what the tests actually assert. A surprising number of them check that a function "returns a truthy value," that a component "renders without crashing," or that an API call "completes successfully." These are not tests. They are wishes with a pass/fail bit attached. The suite is green because it was written to be green.

This is the quiet crisis of AI-assisted development. It is not that the models write bad code. It is that they have industrialized the writing of bad tests, and the industry's main defense against bad code is now being mass-produced by the same systems generating the code.

## Coverage was always a weak proxy. Now it is a lying one.

Test coverage has been a vanity metric for years. A line can be executed by a test that asserts nothing about it. Everyone who has maintained a large codebase knows this. The metric survived anyway because writing tests was expensive enough that a human who bothered to write one usually bothered to make it meaningful.

That economic constraint is gone. An agent can generate 400 tests in ninety seconds. It can also generate 400 assertions that would pass against a stub returning `null`. The cost of producing green pixels has collapsed to near zero, which means the signal value of green pixels has collapsed with it.

You can see the failure mode in the numbers. Teams report coverage climbing from 60% to 95% after adopting agentic coding tools, while the number of production incidents stays flat or rises. Coverage went up. Correctness did not. The tests are measuring the shape of the code, not its behavior.

## What the agents are actually optimizing for

An LLM writing tests is solving a different problem than you are. You want to know whether the code is correct. The model wants to produce test code that looks like test code and runs without error. Those objectives overlap, but they are not the same.

Ask an agent to test a payment function and it will happily write:

```python
def test_process_payment():
    result = process_payment(amount=100, currency="USD")
    assert result is not None
```

That test passes if the function charges the customer, returns a cached value, or returns an error object. It passes if the function does nothing but return a hardcoded dict. It will keep passing after someone deletes the actual charge call. The test does not know what `process_payment` is for. Neither, in a meaningful sense, does the model.

The tells are consistent across tools:

- Assertions that check for existence rather than value (`is not None`, `is not False`, `len(x) > 0`)
- Tests that mock the thing under test, then assert the mock was called
- Snapshot tests regenerated on every run, so they can never fail
- Error-path tests that only confirm "an exception was raised," not which one or why
- Tests named `test_works` or `test_happy_path` with no stated invariant

Each of these is a test that cannot fail for the right reason. A test that cannot fail is not a safety net. It is decoration.

## The vibe check, named honestly

Here is what actually changed. When a human wrote a test, they had to hold the intended behavior in their head and encode it as an assertion. That act of encoding was the value. The test was a byproduct of a person thinking carefully about what correct means.

When an agent writes the test, nobody performs that act. The assertion is generated from the same understanding of the code that generated the code. If the model misunderstood the requirement, the test encodes the misunderstanding. The test and the code agree with each other and disagree with reality. You get a closed loop of mutual confidence.

This is why the phrase "the unit test is now a vibe check" is not a joke. It is a description. The suite passes, the team feels good, and the feeling is the only thing being verified. The test has stopped being an oracle and become a mood.

## What to do about it

The fix is not to ban agents from writing tests. It is to change what you ask them for and what you review.

- Write the assertions yourself. Let the agent scaffold the boilerplate, the fixtures, the setup. You write the line that says what must be true.
- Require tests to fail first. A test you have never seen fail is a hypothesis you have never tested.
- Test behavior at the boundary. Assert on return values, persisted state, and emitted events, not on internal calls.
- Kill mutation testing's excuses. Mutation testing is the one tool that catches assertion-free tests at scale. Run it on the modules that matter.
- Treat coverage as a floor, not a goal. If coverage is your headline metric, you are measuring the wrong thing and the agents will happily optimize it.

None of this is new advice. It was good advice when humans wrote the tests. It became urgent the moment the cost of writing a test dropped below the cost of thinking about one.

## The takeaway

AI did not break your test suite. It revealed that a large fraction of it was never testing anything. The agents just made the emptiness cheap and fast to produce. If your suite is green and you cannot explain what each green checkmark proves, you do not have tests. You have a vibe check with a CI badge.
