A spec drifts one comment at a time. Someone asks for a small change in Slack, you say yes, someone else asks for a corner case, you say yes, and three weeks later the engineer building it is working from a document that no longer matches what anyone agreed to. The original decision is buried under forty replies.

Most PMs I know have tried to fix this with AI. They paste the thread into ChatGPT and ask for a summary. The summary is fine. Then it goes stale in a day, because the thread kept going and nobody re-ran the prompt.

The useful move isn't a better summary. It's a prompt you run on a schedule that produces a **spec drift log** — a short, dated record of what changed since the last version, who asked, and whether it's in or out of scope. Here's the template and how to run it.

## Why summaries fail and drift logs work

A summary flattens history. It tells you the current state and throws away the trail. That's fine for a reader who only wants the gist. It's useless for the person who has to defend a scope decision in a planning meeting six weeks from now.

A drift log keeps the trail. It answers three questions a summary can't:

- What changed since the last time we agreed on something?
- Who asked for it, and did I actually approve it or just not object?
- Is this inside the current scope or does it need a trade-off conversation?

That last one is where most scope creep hides. Nobody approves the extra work. They just don't say no fast enough, and the spec quietly grows.

## The prompt template

Save this somewhere you'll actually find it. Fill in the bracketed parts.

```
You are helping me maintain a product spec for [feature name].

Here is the previous version of the spec:
---
[paste previous spec or drift log]
---

Here is everything that happened since: Slack thread, Jira comments, meeting notes, my own notes.
---
[paste raw material]
---

Produce a drift log with these sections:

1. CHANGES — one line per change. Format: [date] [who] [what changed]. Quote the original message if it's short.
2. IN SCOPE — changes that match the current spec's stated goal.
3. OUT OF SCOPE — changes that expand the goal or add a new user type, integration, or platform.
4. UNRESOLVED — questions raised but not answered.
5. OPEN DECISIONS — things I need to decide this week, with the trade-off spelled out.

Do not summarize the whole thread. Only log what is different from the previous version. If nothing changed, say "no changes."
```

The "do not summarize" line matters. Without it, the model defaults to a summary because that's what most prompts ask for. You have to tell it explicitly that you want a diff, not a digest.

## Run it weekly, not on demand

The failure mode of any AI workflow is that you run it once, feel productive, and never touch it again. Drift logs only work if they're cumulative — each run compares against the last, not against the original spec.

Pick a day. Friday afternoon works for most teams because the week's decisions are fresh and you're already doing close-out work. Set a 20-minute block. Run the prompt. Skim the OUT OF SCOPE and OPEN DECISIONS sections, fix anything the model got wrong, and paste the drift log into the spec document as a dated appendix.

The spec itself stays clean. The drift log is the audit trail underneath it. When someone asks "when did we decide to add SSO to this feature?" you scroll to the week it appeared and find the line.

## What to feed it (and what to leave out)

Garbage in, garbage drift log. The model can only diff what you give it.

**Feed it:**
- The Slack thread from the feature channel, exported as text
- Jira comments on the epic and its child tickets
- Meeting notes from any sync where the feature came up
- Your own quick notes from 1:1s

**Leave out:**
- The whole company Slack. The model will find noise and log it as a change.
- Anything from a private channel you'd have to explain context for. If you need three paragraphs of backstory, it's not a drift item.
- Your opinions. The drift log records what happened, not what you think should happen. That's what OPEN DECISIONS is for.

One trap: don't feed it the design file or the Figma comments unless you're prepared to log every pixel tweak as a change. Visual iteration is not spec drift. Keep the two separate or the log becomes unreadable.

## Where the model gets it wrong

Two failure modes show up again and again.

**It over-logs.** A thread where someone says "looks good" and someone else says "thanks" will produce three "changes" if you don't constrain it. The fix is the "if nothing changed, say no changes" line and a habit of deleting anything that isn't a real decision. Your drift log should be shorter than the raw material, not the same length.

**It under-flags scope.** The model doesn't know your product strategy. It will happily mark a new integration as "in scope" because it sounds related. That's why OUT OF SCOPE is a section you review by hand, not one you trust. The model's job is to surface candidates. Yours is to make the call.

I've found the model is roughly 80% right on CHANGES and maybe 60% right on IN/OUT classification. That's still a huge time save — you're editing a draft, not building one from scratch — but it means you can't paste the output without reading it.

## The part that actually changes behavior

Here's the thing nobody tells you about running this for a few weeks: the drift log starts to change how you respond to requests in the moment.

When you know every "small ask" in Slack is going to show up in Friday's OUT OF SCOPE section with your name next to it, you get faster at saying "let's log that as a separate ticket" instead of "sure, we can probably fit it in." The log doesn't just document scope creep. It makes you less likely to cause it.

That's the real return. Not the saved hour of writing. The behavior change that comes from knowing there's a record.

## A note on tool choice

This works in ChatGPT, Claude, Gemini, or whatever you're using this quarter. The prompt is portable. Don't spend a week evaluating tools — the template matters more than the model, and switching costs are low enough that you can move if one gets noticeably worse.

What does matter: pick a tool that lets you keep a persistent thread or project so the previous drift log is easy to paste back in. If you're copy-pasting from a fresh chat every week, you'll stop doing it by week three.

## Start with one feature

Don't roll this out across your whole portfolio. Pick the feature with the most active Slack thread and the most scope ambiguity — you probably already know which one. Run the prompt this Friday. See what the drift log surfaces.

If it catches one scope change you didn't realize you'd approved, it paid for itself. If it catches three, you'll want to run it on everything.
